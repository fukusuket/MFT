## 1. レビュー所見

### 1.1 資料間で一致している点

- **パースの先にある、絞り込み・相関・説明に価値がある。** CSVを出すだけの既存ツールとはここで差をつける。
- **イベントログが消されていても解析できる。** ログを消した行為そのものも、USNに残る `.evtx` の削除として検出できる。
- **Windows標準ベースラインとの差分**で絞り込む。この切り口は既存ツールにない。
- `$LogFile`、フルフォレンジック、悪性の断定、EDRの代替は対象外とする。
- パスはRewindアルゴリズムで復元し、復元の確からしさ（確定 / 推定 / 不明）を明示する。
- 証拠データは外部に送らず、ローカルで完結させる。

### 1.2 食い違いと採用した方針

| 論点 | Claude案 | Codex案 | 採用 | 理由 |
|---|---|---|---|---|
| 判定の方式 | Sigmaルールのみ。レベルは固定値で、スコアは使わない | 加点・減点で優先度スコアを計算する | **Claude案** | 重みの合算は、なぜその順位になったかを説明できない。Codex案の「重大度と確度を分ける」考え方は、確度を**計算値ではなく事実**（パス解決の状態、MFTとUSNの両方で確認できたか）として表示する形で取り込む |
| 配布と閲覧の形態 | CLIで解析し、自己完結HTML 1ファイルを出力する | localhostのHTTPサーバー＋SQLiteのCase管理 | **Claude案** | 課題C6「担当者間の共有」に直結する。メールで送れて、受け取った側はブラウザで開くだけで済む。SQLiteのCase管理はv1以降の候補とする |
| 収集機能（Collector） | 提供する | 提供しない（KAPE等に任せる） | **提供する（最小限）** | 主対象のP1（情シス担当）はKAPEやVelociraptorを使えない前提である。KAPE等で取得したファイルもそのまま入力にできるようにし、既存の運用も壊さない |
| ルール形式 | Sigma（SigmaHQと互換） | 独自のYAML＋Rust実装。Sigmaはコアにしない | **Claude案** | 開発者がHayabusaのSigmaエンジンを持っており、利用者もSigmaに慣れている。Codexが指摘した「エンティティの相関はSigmaで書きにくい」点は、Sigmaの外で事実として表示することで対応する（6.4節） |
| 判定結果の説明 | ルール名、条件、根拠の値、平易な説明 | 事実 / 推定 / 確度 / 反証 / 推奨確認事項 | **両方を組み合わせる** | Codex案の構成は非専門家にとってわかりやすい。ただし実行時に文章を生成するのではなく、**ルールIDごとに固定の説明ファイル**（解釈・制約・推奨確認事項）を用意する |
| 対象OS | クライアントとServerの両方 | Windows 10 / 11 | **MVPはWin10 / Win11、Serverは次の段階** | ベースラインを生成するCIのコストを、まず小さく抑える |

### 1.3 資料に足りない点（本書で補ったもの）

1. **「ベースライン外であること」をSigmaルールの条件に書けない。** architecture.mdは「独自フィールドを使わない」としているため、research-suspicious-windows-paths.mdが最優先に挙げる「System32にあるベースライン外のPE」をルールとして書けない。コア機能と検知エンジンがつながっていない。
   → 本書では、ベースライン外のファイルを**独立した一覧（標準外ファイル）として常に表示する**ことにした。そのうえで、ベースライン外のイベントを専用のlogsource（`service: baseline_outside`）でも流し、フィールドはSigma標準のまま、ルールで「ベースライン外」に限定できるようにした（6.3節）。
2. **USNの保持期間と、指定した調査期間のずれ。** `$J` はクライアントでは数日〜数週間分しか残らない。指定期間の一部がUSNの範囲外だと、「何もなかった」と誤解されるおそれがある。
   → CLIとUIの両方で、USNが残っている期間を常に表示し、範囲外を含む場合は警告する。
3. **期間フィルタで攻撃の初期を見落とすおそれ。** 検知は全期間に対して行い、期間指定は表示の絞り込みとして扱う。期間外で一致したものも件数として表示する。
4. **「8割の攻撃を検出」の測り方が決まっていない。** 7章で評価方法を定義した。

## 2. 解決する課題

> **イベントログが消されていても、`$MFT` と `$UsnJrnl` だけを使って、「普通のWindowsには無いもの」と「調査期間に起きたこと」を、専門家でなくても数十分で洗い出せるようにする。**

| # | 課題 | 現状 | 本ツールでの解決 |
|---|---|---|---|
| C1 | イベントログが削除されていると、何もわからない | Hayabusa等のログ解析はログがないと使えない。ログの削除は攻撃者の常套手段 | NTFSのアーティファクトだけで解析する。`.evtx` の削除・切り詰めやUSNジャーナルの削除自体も検出する |
| C2 | フルフォレンジックは遅い（準備に数日、転送に1日） | イメージの取得・転送・処理を待つ間に被害が広がる | 収集するのは `$MFT` と `$J`（スパース部分を除く）だけ。圧縮して数十〜数百MBにする |
| C3 | 商用フォレンジックツールは高い | 導入できず、外部委託するかの判断も遅れる | OSSで無償。インストール不要のシングルバイナリ |
| C4 | MFTパーサーはCSVを出すだけで、どこを見ればよいかを示さない | 数十万〜数百万行をExcelで眺めることになる | ルールに一致したものを、根拠と「なぜ要確認か」の説明つきで、レベル順に並べる |
| C5 | 見なくてよいものを大量に見る必要がある | Windows Update、Defender、ブラウザ等のノイズが大半を占める | Windows標準ベースラインを差し引き、期間で絞り込む |
| C6 | 担当者間・組織間で状況を共有しにくい | 生データは大きく、扱うには専門知識が要る | HTML 1ファイルのレポートにする。ブラウザで開くだけで、全員が同じ画面を見て話せる |
| C7 | IoCやシグネチャにない、未知の攻撃ツールを見逃す | IoC、Sigma、YARAは既知の悪性を前提にしている | 悪性の特徴ではなく、「標準との差分」で浮かび上がらせる |

**本ツールでわからないこと**（UIにも明記する）：ファイルを作成・実行したユーザーやプロセス、ファイルの中身（residentデータを除く）、実行の有無と回数、USNの保持期間より前の活動。

## 3. 想定ユーザ

| # | ペルソナ | 使う場面 | スキル | 本ツールに求めること |
|---|---|---|---|---|
| **P1（主）** | 中堅・中小企業の情シス担当（セキュリティの専門家ではない） | ランサムウェア感染やEDRのアラート時に、最初に現場で対応する | Windowsの管理はできるが、フォレンジックの経験はない | USBで収集→ダブルクリックでレポート。専門用語なしで「次に何をすべきか」がわかる |
| **P2** | 事業会社のCSIRT / SOC担当（セキュリティベンダー以外） | アラート後に、侵害の範囲を複数の端末で特定する | DFIRの基礎知識があり、Hayabusaも使える | 共通のルールとベースラインで調査の品質をそろえる。Hayabusaのタイムラインとマージできる |
| **P3** | 予算の少ない組織のセキュリティ担当（自治体、教育機関、医療機関、中小MSP） | 定期的な侵害調査、インシデント時の一次調査 | 人によって差が大きい | 無償で使える。自組織のベースライン（ゴールデンイメージ）を差し引ける |
| P4（副） | DFIRの専門家・フォレンジックベンダー | フルフォレンジックの前のトリアージ。P1〜P3からレポートを受け取る | 高い | 生のレコードまで辿って自動判定を検証できる。CSVやJSONLを出力できる |

**設計上の優先順位**：P1が迷わずに使えることを最優先にする。P4向けの詳細情報は、詳細画面とエクスポートに出し、P1の画面を複雑にしない。

|---|---|---|---|---|---|---|---|
| 主な目的 | NTFSのトリアージ（何を見るべきか） | パース | パース | パース＋相関＋レポート | 閲覧 | イベントログのトリアージ | フルフォレンジック |
| 出力 | HTMLレポート＋CSV / JSONL | CSV | JSON / CSV | HTML / CSV / SQLite | 画面上の表 | CSV / JSONL / HTML | 独自形式 |
| **Windows標準ベースラインとの差分** | **◎（コア機能）** | × | × | × | × | — | △（ハッシュセット） |
| 期間による絞り込み | ◎ | × | × | ○ | △ | ◎ | ○ |
| Rewindによるパス解決 | ○ | × | × | ○ | × | — | — |
| 検知ルール | Sigma（SigmaHQから流用＋自作） | ×（列で示すのみ） | × | 独自ルール | × | Sigma | 独自 |
| イベントログが消されても使えるか | ◎ | ○ | ○ | ○ | ○ | × | ○ |
| 判定理由の説明 | ルール、根拠の値、平易な説明 | × | × | △ | × | ○ | △ |
| 非専門家にも使えるか | ◎（目標） | × | × | △ | △ | ○ | × |
| 費用・開発状況 | 無償 / 新規 | 無償 / 活発 | 無償 / 活発 | 無償 / **2026-07にアーカイブ** | 無償 / 稼働中 | 無償 / 活発 | 高額 |

**一言でいうと**
- **MFTECmd・mft crateとの違い**：これらは「正確にパースする」ところまで。本ツールはその先の、絞り込み・相関・説明を自動化する（パーサーとしてはmft crateを採用する）。
- **usnjrnl-forensicとの違い**：形は最も近いが、ベースライン差分という切り口はなく、開発も終了している。
- **Hayabusaとの関係**：競合ではなく補完。Hayabusaがイベントログからイベントを抽出するように、本ツールはファイルシステムからファイルとその活動を抽出する。出力の列をそろえ、1つのタイムラインにマージできるようにする。
- **IoC / Sigmaとの着眼点の違い**：「既知の悪性」を探すのではなく、「標準との差分」と「期間」を見る。そのうえで、既知の悪性パターンもSigmaルールで重ねて検出する。

## 5. MVP

### 5.1 MVPのゴール

> **P1が、Windows 10 / 11のクライアント1台から収集して、30分以内にHTMLレポートを開き、「最初に何を確認すべきか」を判断できる。**

### 5.2 MVPに含めるもの

| # | 機能 | 内容 |
|---|---|---|
| M1 | `collect` | Windows x64のシングルexe。`\\.\C:` をRawで読み、`$MFT`、`$J`（スパース部分を除く）、`$Boot`、`$Secure:$SDS` と `meta.json`（ホスト名、OSビルド、UBR、タイムゾーン、取得時刻、ハッシュ）を、1つのzipにまとめる。読み取り専用で動作する |
| M2 | 入力の受け付け | M1のzipに加え、KAPE・Velociraptor・FTK Imagerで取得した `$MFT` / `$J` のディレクトリも入力にできる |
| M3 | パース | `$MFT`（mft crateを使う。4Knのテストを必須とする）と、`$J` のUSN V2 / V3 |
| M4 | パス解決 | 親参照＋シーケンス番号の検証＋Rewind。結果を `resolved` / `inferred` / `unknown` で示す |
| M5 | ベースライン差分 | Win10 22H2と、Win11 24H2 / 25H2のx64版（日本語・英語）。ビルドを自動で判定し、一致するビルドがなければ最も近いビルドを使う |
| M6 | 検知 | Sigmaエンジン（単体ルール＋correlationの `event_count` と `temporal_ordered`）。初期ルールは、SigmaHQのうちファイル名だけで判定するもの（約120本）と、自作ルール（悪用されやすいパス、なりすまし、アンチフォレンジック、ランサムウェア） |
| M7 | 期間 | `--from` / `--to` で表示を絞る（検知自体は全期間に対して行う）。USNが残っている期間を表示し、指定期間とずれていれば警告する |
| M8 | HTMLレポート | 自己完結の1ファイル。画面は、サマリ、要確認リスト、標準外ファイル、タイムライン、ファイル詳細の5つ。日本語と英語に対応 |
| M9 | エクスポート | `findings.jsonl` と `timeline.csv`（Hayabusa / Takajoのタイムラインとマージできる列構成） |

### 5.3 MVPに含めないもの（次の段階以降）

| 機能 | 予定 | 理由 |
|---|---|---|
| Windows Serverのベースライン | v1.0 | ベースライン生成CIのコスト |
| 自組織のベースライン（`baseline build`） | v1.0 | 標準ベースラインの品質を先に固める |
| ツリー差分ビュー | v1.0 | 標準外ファイルの一覧で代用できる |
| 複数端末の横断比較 | v1.x | まず1台で価値を確認する |
| residentデータへのYARA-X | v1.x | オプション機能 |
| WASM版（ブラウザにドロップして解析） | v2 | GB級の$MFTではメモリが足りない |
| SQLiteのCase管理、localhostサーバー | 検討 | MVPには自己完結HTMLで足りる |
| `$LogFile`、イメージ全体の解析、Linux / macOS | 対象外 | — |

### 5.4 MVPの完了条件

| 指標 | 目標 |
|---|---|

## 6. アーキテクチャ

### 6.1 設計方針

1. **1つのRustコアに、複数の出口**：CLI、HTMLレポート、（将来の）WASM版で同じ解析コードを使う。
2. **重い処理はCLI、閲覧はブラウザ**：ブラウザには絞り込んだ結果だけを渡す。
3. **成果物は自己完結HTML 1ファイル**：サーバーもインストールも不要で、外部とは通信しない。
4. **判定はルールファイルにすべて書く**：コアは事実（フィールド）を渡すだけで、コードの中に判定を埋め込まない。
5. **計算スコアは使わない**：レベルはルールの固定値をそのまま使う。同じ入力からは必ず同じ結果になる。
6. **ベースラインとルールはデータとして、本体とは別に管理する**：Hayabusaのルールリポジトリと同じ運用にする。
7. **生データまで辿れるようにする**：すべてのFindingから、元のレコード（ファイル、オフセット、エントリ番号、USN）を参照できる。

### 6.2 全体構成

```
 ┌─────────────── 調査対象のWindows端末 ───────────────┐
 │ tool collect                                         │
 │   \\.\C: をRawで読む → $MFT / $J（スパース除去）/ $Boot / $SDS │
 │   + meta.json（OSビルド、UBR、TZ、取得時刻、SHA-256）     │
 └───────────────────────┬─────────────────────────────┘
                         │ collection.zip（数十〜数百MB）
                         │ ※KAPE等で取得したファイルも入力にできる
                         ▼
 ┌─────────────── 解析用PC（Windows / macOS / Linux）────────┐
 │ tool analyze                                           │
 │  ┌ Ingest ─ 検証（シグネチャ、fixup、USNの範囲、破損件数） │
 │  ├ Parse ── MftParser / UsnParser                      │
 │  ├ Resolve ─ 親参照＋シーケンス検証＋Rewind               │
 │  ├ Normalize ─ %USERPROFILE%、SID、GUID、WinSxS等を正規化 │
 │  ├ Baseline ─ 標準 / 標準外を判定（fst）  ◄── Baseline DB │
 │  ├ Facts ── timestompの手がかり、ADS、Zone.Id、所有者SID │
 │  └ Detect ── Sigma（単体＋correlation）  ◄── Rules       │
 └───────────────────────┬─────────────────────────────┘
                         │ report.html（データを埋め込んだ1ファイル）
                         │ findings.jsonl / timeline.csv
                         ▼
 ┌─────────────── 任意のブラウザ（オフライン）────────────┐
 │ サマリ / 要確認リスト / 標準外ファイル / タイムライン / 詳細 │
 └──────────────────────────────────────────────────────┘
```

### 6.3 解析の流れと、ベースライン・Sigmaの関係

```
 全USNイベント + 全MFTエントリ
        │
        ├──► [Detect A] Sigma（logsource: file_event / file_delete / file_rename / file_change）
        │      全件に適用する。標準のファイル（.evtx等）の削除も対象になる
        │
        ├──► [Baseline] 正規化したパスでfstを引く ─► 標準外のもの
        │                                              │
        │      ┌───────────────────────────────────────┤
        │      ▼                                       ▼
        │  [Detect B] Sigma（logsource:              [標準外ファイル一覧]
        │   service: baseline_outside）               ルールに一致しなくても表示する
        │   例: System32にあるベースライン外のPE         （本ツールの核となる出力）
        │
        └──► Findings = Detect A + Detect B の一致（ルールを合算せず、すべて列挙する）
```

- **標準外ファイル一覧**は、ルールに一致しなくても表示する。未知のツールはここで見つける（課題C7）。
- `service: baseline_outside` は、Sigmaのlogsourceの仕組みで「ベースライン外のイベントだけ」を対象にする方法である。フィールドはSigma標準（`TargetFilename` 等）のままなので、SigmaHQのルールはそのまま動く。

### 6.4 データモデル

```text
Entry        { entry, seq, flags, si_times[4], fn_times[4], size, ads[], parent_ref, resident, sec_id }
UsnEvent     { usn, time, frn(entry,seq), parent_frn, name, reasons[], source_offset }
ResolvedPath { path, normalized, state: resolved | inferred | unknown }
FileFacts    { baseline: standard | outside | n/a,
               timestomp_hints[]（SI<FN, uSecZeros, SI作成 < OSインストール日）,
               zone_identifier{zone_id, host_url, referrer_url}, ads[], deleted,
               owner_sid, seen_in: mft | usn | both }
Finding      { target, matched_rules[{id, title, level, condition, evidence}],
               facts: FileFacts, evidence_refs[{artifact, offset, record_id}] }
```

`FileFacts` は判定もレベルも付けない**事実**である。一覧の列やフィルタとして表示するだけにする。Codex案の「確度」は、`ResolvedPath.state` と `seen_in` の2つの事実で表す。

### 6.5 コンポーネントとリポジトリ構成

```
tool/                       # Cargo workspace
├── crates/
│   ├── core/               # model, parse(mft/usn), resolve(rewind), normalize, baseline, facts
│   ├── sigma/              # Sigmaエンジン（Hayabusaの知見を流用）
```

| 項目 | 方針 |
|---|---|
| MFTパーサー | `mft` crate（Apache-2.0 / MIT）。4Kn（512バイト単位のfixup）のテストを必須とする |
| USNパーサー | 公開仕様に基づき自前で実装する（V2 / V3、V4は需要に応じて） |
| ベースラインの検索 | `fst` crate。ビルドごとに作り、zstdで圧縮して配布する |
| ベースラインの生成 | Packerで評価版ISOからVMを作り、「素の状態 → Windows Update後 → 代表的なアプリの導入後」の各段階で `collect` を実行する。複数回の結果の和集合を取り、レビューしてからリリースする |
| ルールの説明文 | ルールIDをキーにした翻訳ファイル（`explain/ja/<rule-id>.yml`）に、解釈・制約・推奨確認事項を書く。Sigmaのルール本体には独自フィールドを足さない |
| 堅牢性 | `forbid(unsafe_code)`。cargo-fuzzをCIで実行する。不正なレコードがあっても全体を止めず、スキップした件数をレポートに出す |
| 正確性 | MFTECmdとの差分テスト（パース結果）、usnjrnl_rewindとの差分テスト（パス解決） |
| プライバシー | 外部と通信しない。`--mask-users` でユーザー名を伏せられるようにする |
| ライセンス | 本体（Rust、Viewer、collector）は **AGPL-3.0**（Hayabusaと同じ）。ルール（`tool-rules`）は **DRL 1.1**（SigmaHQ、hayabusa-rulesと同じ）。ベースラインのデータの扱いは別に決める。詳細は [engineering-review.md](engineering-review.md) のR7 |

## 7. 検知精度の評価方法

「8割の攻撃を検出」を次のように定義し、CIで回帰を監視する。

- **コーパス**：管理されたVMで攻撃シナリオを再現し、取得した `$MFT` / `$J` に正解のラベルを付ける。シナリオの例：ツールの配置→実行→削除、Startupへの永続化、なりすまし名、`.evtx` の削除、SDelete、ランサムウェア風の大量リネーム、アーカイブの作成→削除。これにDFIR Madness、DEF CON DFIR CTF、NIST CFReDSなどの公開データを加える。
- **再現率**：正解ラベルの付いたファイルのうち、「要確認リスト」か「期間内の標準外ファイル一覧」に出たものの割合（目標80％以上）。
- **ノイズ**：同じVMで正常な操作（Windows Update、Office・ブラウザの更新）だけを行った場合に、critical / high に一致した件数（目標は0件に近づける）。
