# アーキテクチャ提案

## 1. 方針

本ツールは、`$MFT` と `$UsnJrnl:$J` をローカル環境で解析する、Rust製のブラウザベースアプリケーションとする。

設計上の中心はパーサーではなく、次の処理である。

1. 異なるアーティファクトを共通のファイル実体へ関連付ける
2. Windowsベースラインと既知の正常活動によってノイズを減らす
3. 複数の根拠からFindingを生成する
4. 事実、推定、確度を区別して表示する

初期版は単一端末・単一案件をローカルで解析するデスクトップ相当の構成とする。サーバー運用や複数ユーザー管理はMVPに含めない。

## 2. 対象範囲

### 対象

- `$MFT`
- `$UsnJrnl:$J`
- Windows 10およびWindows 11のNTFS
- 取得済みアーティファクトのオフライン解析
- Windowsビルド等を指定したベースライン比較
- 期間指定、相関、Finding生成、レポート出力

### 対象外

- `$LogFile`
- Linux、macOSおよびNTFS以外のファイルシステム
- ディスクイメージ全体の解析
- ライブ端末からのアーティファクト取得
- マルチテナント、認証、中央管理
- 悪性判定の自動確定

アーティファクト取得はRawCopy、KAPE、Velociraptor等の既存手段へ委ねる。取得機能を本体から分離することで、管理者権限、端末への影響、証拠保全に関する責任範囲を明確にする。

## 3. 全体構成

```text
                       ┌─────────────────────┐
                       │ Browser UI          │
                       │ import / findings   │
                       │ timeline / evidence │
                       └──────────┬──────────┘
                                  │ localhost HTTP/API
                       ┌──────────▼──────────┐
                       │ Rust Application    │
                       │                     │
Input files ──────────►│ Ingestion           │
  $MFT                 │ Parsing             │
  $UsnJrnl:$J          │ Normalization       │
                       │ Correlation         │
Baseline packages ────►│ Enrichment          │
Rule packages ────────►│ Finding Engine      │
                       │ Query / Export      │
                       └──────────┬──────────┘
                                  │
                       ┌──────────▼──────────┐
                       │ Case Storage        │
                       │ SQLite + raw files  │
                       └─────────────────────┘
```

ブラウザは表示層として使用し、解析処理と証拠データはローカルのRustプロセス内に置く。外部サービスへのアップロードを必須にしない。

## 4. コンポーネント

### 4.1 Case Manager

案件単位で入力、解析条件、使用したベースライン、ルール、生成結果を管理する。

主な責務：

- Caseの作成、オープン、アーカイブ
- 入力ファイルのSHA-256計算と記録
- ファイルサイズ、取得元、取得日時、タイムゾーンなどの記録
- 解析バージョン、ベースラインID、ルールセットIDの保存
- 再解析時の再現性確保

元の証拠ファイルは読み取り専用として扱い、パーサーが変更しない設計にする。

### 4.2 Ingestion and Validation

解析前に入力の種類と品質を検査する。

検査項目：

- ファイル種別とシグネチャ
- MFTレコードサイズ、fixup、破損レコード数
- USNレコードのバージョン、境界、スパース領域
- 入力同士の整合性
- 解析可能件数とスキップ件数
- 切り詰めや破損の可能性

不正なレコードがあっても解析全体を停止せず、回復可能な範囲を処理し、欠落を診断情報として残す。

### 4.3 Artifact Parsers

アーティファクト固有のバイト列を、型付けされたレコードへ変換する。

```text
Parser trait
├── MftParser
└── UsnJournalParser
```

MFTパーサーでは既存のRust crateの採用を評価し、不足する属性や破損時の挙動のみを補完する。USNパーサーは公開仕様を基準にV2を優先し、V3/V4は実データと需要に応じて追加する。

パーサー層では異常判定を行わない。入力に存在する事実と、解析上の警告だけを返す。

### 4.4 Normalized Evidence Model

MFTとUSNに共通する情報を正規化する。ただし、アーティファクト固有情報を失わない。

主要エンティティ：

- `FileIdentity`：MFTエントリ番号とシーケンス番号
- `FileSnapshot`：MFTから得た現在または削除済みの状態
- `FileEvent`：USNから得た時系列イベント
- `ResolvedPath`：復元したパスと確度
- `EvidenceRef`：元ファイル、オフセット、レコードIDへの参照
- `Finding`：複数の証拠から生成した調査所見

例：

```text
FileIdentity
  entry_number
  sequence_number

FileEvent
  identity
  parent_identity
  timestamp
  usn
  reasons[]
  name
  source_offset

ResolvedPath
  path
  confidence: exact | inferred | unresolved
  supporting_evidence[]
```

NTFS固有のUSN、名前空間、属性、resident/non-residentなどは拡張フィールドとして保持する。

### 4.5 Path Resolver and Correlation Engine

MFTエントリ番号とシーケンス番号を使って、MFTとUSNを関連付ける。

主な処理：

- MFTの親参照からパスを構築
- シーケンス番号を確認し、再利用されたエントリとの誤結合を防止
- USNの親参照とファイル名からイベント時点のパス候補を生成
- `RENAME_OLD_NAME` と `RENAME_NEW_NAME` を近接USNとして関連付け
- FILE_CREATEからFILE_DELETEまでのライフサイクルを構成
- パスを `exact`、`inferred`、`unresolved` に分類

証拠が不足している場合は、もっともらしいパスを確定値として保存しない。複数候補を許容する。

### 4.6 Baseline Engine

対象Windows環境で正常と期待されるファイルを照合する。

ベースライン識別子：

- Windows製品名
- バージョンおよびビルド番号
- SKU
- アーキテクチャ
- 表示言語
- 更新レベルまたは作成日

ベースラインエントリの候補：

- 正規化パス
- ファイル名
- サイズまたはサイズ範囲
- ハッシュ（取得できる場合）
- Microsoft署名などの由来情報
- オプショナル機能や言語依存の条件
- 想定されるファイル属性

判定結果は `present` / `absent` だけにせず、次のように分類する。

- `expected`：対象環境で存在が期待される
- `known-optional`：機能や構成によって存在し得る
- `unknown`：ベースラインに情報がない
- `mismatch`：同一パスだが属性などが期待値と異なる
- `not-applicable`：対象ベースラインでは評価できない

ベースラインに存在しないことだけで重大度を上げすぎない。これはFindingを構成する一つの信号として扱う。

### 4.7 Finding Engine

正規化した証拠へルールを適用し、調査所見を生成する。

初期ルールの例：

- 指定期間内に作成された実行可能ファイルまたはスクリプト
- 作成後、短時間でリネームまたは削除されたファイル
- ユーザー書き込み可能領域に置かれた実行可能ファイル
- Windowsベースラインにないシステムディレクトリ配下のファイル
- `$SI` と `$FN` の不自然な時刻差
- USNのFILE_CREATEとMFTタイムスタンプの不整合
- `BASIC_INFO_CHANGE`を伴う不自然な時刻変更
- ADSの存在またはNAMED_DATA系イベント
- `.evtx` の削除または切り詰め
- 短時間に集中した大量リネーム・上書き
- Prefetchファイルの作成・更新による実行の間接的示唆

各Findingは最低限、次を持つ。

```text
Finding
  id
  title
  severity
  confidence
  summary
  facts[]
  inferences[]
  evidence_refs[]
  counter_indicators[]
  recommended_actions[]
  rule_id
  rule_version
```

`severity` は影響の大きさ、`confidence` は証拠の確からしさとして分離する。「重大だが確度が低い」といった結果を表現できるようにする。

### 4.8 Scoring and Suppression

スコアは悪性確率ではなく、調査優先度として扱う。

加点例：

- 不審な保存場所と拡張子
- 短期間での作成・リネーム・削除
- ベースラインとの不一致
- 時刻情報の矛盾
- 複数の独立した証拠による裏付け

減点例：

- 対象ビルドのベースラインと一致
- 既知のWindows Update活動と整合
- 信頼できる許可リストと一致
- パスやファイルIdentityの確度が低い

重大度を計算式だけで決めず、ルールで最低・最高レベルを制約する。スコア構成要素をUIから確認できるようにする。

### 4.9 Query and Web API

RustアプリケーションはlocalhostのみにHTTPサーバーを公開し、UIへ次の機能を提供する。

- Caseと入力の管理
- 解析の開始、進捗、キャンセル
- Finding一覧、絞り込み、並び替え
- ファイル単位のライフサイクル表示
- 証拠レコードへのドリルダウン
- 統計、期間分布、ディレクトリ分布
- CSV、JSON、HTMLレポートの出力

APIを最初から内部境界として定義することで、将来CLI、外部連携、サーバーモードを追加しやすくする。ただしMVPでは公開APIの互換性を保証しない。

### 4.10 Browser UI

UIは「生レコード検索」よりFindingを入口にする。

主要画面：

1. **Import**：入力ファイル、対象Windows、タイムゾーン、調査期間を指定
2. **Overview**：解析品質、対象期間、Finding分布、重要な注意事項を表示
3. **Findings**：重大度、確度、期間、パス、ルールで絞り込み
4. **File Activity**：一つのファイルに関するMFT情報とUSNイベントを時系列表示
5. **Evidence**：元レコード、オフセット、パース値を確認
6. **Report**：選択したFindingと注記を共有用に出力

色だけで重大度や確度を表現せず、文字とアイコンを併用する。

## 5. データ保存

### SQLite

CaseごとにSQLiteデータベースを作成する。

採用理由：

- 単一ファイルで移動・共有しやすい
- サーバーの構築が不要
- トランザクションとインデックスを利用できる
- Rustと相性がよい
- 数百万件規模の検索に対応しやすい

USN時刻、MFTエントリ番号、シーケンス番号、親参照、正規化パス、Finding IDへインデックスを設定する。大量挿入はバッチトランザクションで行う。

### Caseディレクトリ例

```text
case-name/
├── case.json
├── evidence/
│   ├── $MFT
│   └── $J
├── case.sqlite
├── baselines/
│   └── manifest.json
├── rules/
│   └── manifest.json
└── exports/
```

入力をCaseへコピーするか外部参照するかは選択可能にし、どちらの場合もハッシュと実パスを記録する。

## 6. 技術スタック候補

### Rustバックエンド

- 非同期ランタイム：Tokio
- ローカルHTTP：Axum
- SQLite：SQLxまたはrusqlite
- シリアライズ：Serde
- エラー管理：thiserror、anyhowはアプリケーション境界に限定
- ロギング：tracing
- CLI：clap

MFT解析crateは、対応属性、破損耐性、ライセンス、更新状況、性能、正解データとの一致を評価して採用を決める。

### フロントエンド

TypeScriptを使用し、React、Vue、Svelte等の小規模SPAを候補とする。フレームワークよりも、巨大テーブルの仮想スクロール、ローカル動作、静的アセットとしてRustバイナリへ埋め込めることを重視する。

初期版では複雑な可視化ライブラリを避け、Finding一覧、詳細ペイン、簡潔なタイムラインを優先する。

### 配布形態

優先案は、単一のRustバイナリを実行するとlocalhostでWeb UIが起動する形である。

```text
mft-triage analyze --case ./case-001
# http://127.0.0.1:<random-port> を表示
```

ブラウザの自動起動は任意とし、CLIのみで解析・エクスポートできる経路も残す。将来的にTauri等でラップできるが、MVPではWeb UIと解析エンジンの分離を優先する。

## 7. ルール形式

初期段階では、汎用DSLを先に作らず、Rustで実装した型安全なルールとデータ駆動の設定を併用する。

- 単純なパス、拡張子、期間、Reason条件：YAML等のデータルール
- 相関や時系列を必要とする検出：Rust実装
- 各ルールにID、説明、バージョン、参考情報、重大度、必要な証拠を付与
- ルール単位のテストケースを用意

Sigma対応はコア機能にしない。Sigmaはログイベントを主対象としており、NTFSのエンティティ相関を無理に表現すると保守性が低下する。

## 8. ベースラインの生成と配布

ベースラインは本ツールの検知品質を左右するため、解析エンジンから独立したバージョン付きパッケージとする。

生成パイプライン案：

1. クリーンなWindowsイメージをビルド、SKU、言語、アーキテクチャごとに用意
2. 初回起動後の規定状態を統一した手順で取得
3. `$MFT` を解析してベースライン候補を生成
4. 更新プログラムやオプショナル機能による差分を記録
5. manifest、生成条件、入力ハッシュを付けて署名
6. CIで過去パッケージとの差分と異常な増減を検査

ベースラインが完全であると仮定しない。対象環境と厳密に一致しない場合、UIに適合度と制約を表示する。

## 9. セキュリティと証拠保全

- HTTPは既定で `127.0.0.1` のみにbindする
- 外部ネットワーク送信は既定で無効にする
- 入力ファイルを読み取り専用で開く
- 入力と出力のハッシュを記録する
- HTMLレポートやファイル名を表示する際はエスケープする
- 巨大・破損・細工された入力を想定し、境界値検査とメモリ上限を設ける
- パーサーのpanicをCase全体の破損へ波及させない
- ベースラインとルールパッケージの署名を検証する
- VirusTotal等の外部照会は、明示的な同意を必要とするオプションとして分離する

## 10. 性能設計

- 入力をストリーミングし、全レコードをメモリに保持しない
- パース、正規化、DB書き込みを境界付きチャネルで接続する
- SQLiteへの挿入はバッチ化する
- MFTの親子関係索引を作成してからパスを解決する
- Finding生成は必要な列のみを走査する
- UIへ全レコードを一括送信せず、ページングまたはカーソルを使用する
- 解析段階ごとに進捗、処理件数、スキップ件数を表示する

速度だけでなく、同じ入力から同じ結果を得られる決定性を優先する。

## 11. テスト戦略

### パーサーテスト

- 最小構造、境界値、破損fixup、切り詰めレコード
- MFTレコード再利用とシーケンス番号
- 複数のFILE_NAME属性、ADS、residentデータ
- USN V2、複合Reason、リネーム、削除、スパース領域
- 既存ツールとの出力差分テスト

### 相関テスト

- 正常な親子関係
- 親レコードの削除・再利用
- 同一エントリ番号で異なるシーケンス番号
- リネーム前後の対応
- パス不明時に断定しないこと

### 検知テスト

各ルールに対して、陽性、陰性、境界条件の小さなデータセットを用意する。期待するFinding、重大度、確度、根拠を固定し、変更時にレビューできるようにする。

### End-to-Endテスト

管理されたWindows VM上で操作シナリオを実行し、取得した `$MFT` と `$J` を正解付きコーパスとして保存する。

例：

- ファイル作成、変更、リネーム、削除
- ADS作成
- タイムスタンプ変更
- `.evtx` の削除または切り詰め
- 大量リネーム
- Windows Updateなどの正常な大量変更

## 13. 重要な設計判断

1. **`$LogFile`を扱わない**：短い保持期間と高い実装・検証コストに対して、初動トリアージで得られる価値が限定的なため。
2. **取得機能を分離する**：既存の信頼できる取得手段を利用し、解析に集中するため。
3. **Findingを中心にする**：レコードを見せるだけでなく、調査すべき理由を提示するため。
4. **重大度と確度を分離する**：不完全な証拠を過度に断定しないため。
5. **ローカルファーストにする**：機密性の高い証拠を外部へ送らず、導入負担を抑えるため。
6. **生データへの参照を保持する**：自動判定の説明可能性と検証可能性を確保するため。
7. **ベースラインを信号の一つとして扱う**：差分だけで悪性と誤判定しないため。
